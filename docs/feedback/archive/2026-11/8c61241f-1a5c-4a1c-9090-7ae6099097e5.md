**frank890417** · 2026-11-17 00:45

Thanks for reporting this — I checked it rather than assuming, and the answer is more specific than "email login is missing".

**Email sign-in is built and it is live.** The feedback widget supports three methods, and all three are compiled into the bundle currently served from the site:

- `src/scripts/feedback/widget.ts` renders an email field plus a send button whenever `email` is in the provider list
- `src/scripts/feedback/backend.ts` calls Supabase `signInWithOtp` (a magic link)
- the deployed repo variable is `PUBLIC_FEEDBACK_PROVIDERS = google,github,email`
- the live bundle served at `/_astro/FeedbackWidget.astro_astro_type_script_index_0_lang.C6TZy_CH.js` contains both `email` and the `signInWithOtp` call

There is also **Google** sign-in, which your report does not mention. You wrote that GitHub is the only option, so something is stopping two of the three methods from reaching you.

**Two possibilities remain, and I could not separate them from outside:**

1. **The magic link is never delivered.** The button would appear and respond normally, but the email provider on the Supabase side would have to be enabled for the mail to actually go out. Checking that needs access to the Supabase dashboard, which the maintainer has and this routine does not.
2. **The option is there but does not read as one.** The panel shows two OAuth buttons first, then a thin divider, then a plain email input with a secondary-styled button. If the divider is faint on your screen, the email field can look like part of the form you were already filling in rather than a third way to sign in.

I did not try sending myself a magic link, because that would put a real address into a live auth flow and create a real sign-in attempt. That is the maintainer's check to run, not this routine's.

Your report is useful either way: if it turns out to be (2), then the fix is ours and it is a layout problem, not a missing feature. Leaving this open with the diagnosis attached so whoever has the Supabase access can settle (1) in about a minute.

**frank890417** · 2026-11-17 02:02

Follow-up on the diagnosis above — I could narrow it to one cause without touching anyone's address.

**Email sign-in is switched on.** Reading the project's public auth settings (`/auth/v1/settings`, the same public key the site already ships) returns `github: true, google: true, email: true`. So the option is enabled on the server, not just in the page.

**The likely reason the link never arrives:** Supabase's built-in mail server only delivers to members of the project's own team. Their docs: _"Unless you configure a custom SMTP server for your project, Supabase Auth will refuse to deliver messages to addresses that are not part of the project's team … All other addresses will fail with the error message Email address not authorized."_ (https://supabase.com/docs/guides/auth/auth-smtp). For a reader who isn't on the team, the email sign-in looks available and then silently never arrives — which matches what you ran into.

**What fixes it** is configuring a custom SMTP sender in the Supabase dashboard (Authentication → SMTP). That needs dashboard access and an email-sending service, so it's for the maintainer to do; until then GitHub and Google are the sign-in options that work for everyone. Leaving this open for that step. Thanks again — this one would have stayed invisible without your report.
