## 觸發

哲宇看了一則前端 CI 壓到兩分鐘的推文，請總管把三個 repo 的 CI／CD 都加速。這班負責 Taiwan.md，界線是檢查只能變快不能變少、部署產物要一樣、不碰 routine 與 `knowledge/`。

## 先量，再挑招

改之前用 `ci-timing.py` 量了基準：部署中位 13.7 分（Build 368 秒、上傳產物 119 秒、deploy-pages 158 秒），Sticky viewport 7.1 分、i18n smoke 7.3 分、Engineering contracts 2.9 分。每條 job 的 checkout 都要 50 秒左右，因為 HEAD 工作樹有 1.16GB。

一開始以為部署 build 換 x86 會快，因為閘門在 x86 上的 Astro 比部署的 ARM 快一分鐘。照 advisor 的提醒做了同 commit 對照（`zz-ci-speed-bench.yml`，只在分支跑、不部署）：ARM 351／339 秒、x86 310／387 秒，沒有穩定的差距，而且 x86 的產物有 4 個檔大小不同。維持 ARM。同一次對照量出兩個真正的卡點：上傳是 node 單執行緒在做等級 6 的 zip 壓縮，6.1GB 的 tar 要 100 秒，等級 1 只要 63 秒。`status.py` 那條 `git log --name-only` 在 blobless clone 下做改名偵測，逐個 blob 上網抓，要 15 到 40 秒，加 `--no-renames` 後 0.7 秒。本機比對 `--json` 輸出，除了時間戳逐字相同。

## 改了什麼

部署：Markdown 契約、frontmatter、文章健康全掃移到同時跑的 `validate` job，deploy 等兩者都綠。`upload-pages-artifact@v5` 拆成原樣的 tar 加 `upload-artifact`（同一個 SHA），只改壓縮等級為 1。字型閘門只抓 `scripts/tools`，`npm i` 加 `--ignore-scripts` 避開 postinstall 的 sync.sh。Sticky 與 i18n 兩條閘門在 PR 沒動到 OG 圖的輸入時略過產圖（`generate-og-images.mjs` 新增 `OG_SKIP=1`，清單跟 deploy 的偵測同一份），i18n 因此也不用裝 Playwright。push 到 main 照舊整套，判斷不出 PR 改了什麼時也照舊產圖。Engineering contracts 拆成 contracts／types／subprojects 三條並行。UI 語言閘門與 feedback-db 改 sparse checkout，本機比對三支檢查的輸出逐字相同。

拆 job 第一次跑紅了兩條，都是隱含的前置：fork-graph 要 PyYAML，原本是前面 pytest 那步順手裝的。harvest/ui 的 build 往上讀根目錄 tsconfig，要根目錄 node_modules。補上後全綠。

## 驗收

產物：同 commit 舊版對舊版先量雜訊，og-images 會因快取來源不同而有幾張大小不一，其餘逐檔相同。舊版對新版除 og-images 外 26,513 個檔大小逐檔相同，og-images 數量同為 5,196。檢查數：pytest 958 通過、14 略過，node 測試各組數量、vitest 77、astro check 1,544 個檔 0 錯誤，前後一致。sticky 量 10 頁、i18n 77 項 12 語，前後一致。

合併後第一次部署（run 44036804881）因為合併 commit 動到 OG 產生器而全量重產 OG（多 108 秒），全程仍從 14.4 降到 13.4 分：上傳 119 降到 66 秒，deploy-pages 158 降到 136 秒（壓縮等級 1 沒有拖慢它），字型閘門 83 降到 31 秒。正式站首頁、`/en/`、`/about/`、`.well-known/apple-app-site-association` 都回 200，`dashboard-status.json` 產生時間落在這次 run 內。Engineering contracts 3.2 降到 2.3 分。
