## 量到的現況

最近 50 次成功部署，push 到上線中位 622 秒；最近 150 次部署有 62 次被下一筆 push 取消，把取消算進去最慢的一筆等了 35.5 分。622 秒的去向是 astro 產頁 239、GitHub Pages 部署 126、prebuild 97、打包上傳 76、checkout 與環境 50。

兩件以前沒量過的事決定了後面的排序。第一，astro 產頁幾乎只用一顆核心：把 `concurrency` 從 8 改成 1，本機牆鐘只從 111 秒變成 125 秒，CI 上單次建置的 CPU 使用是 143%，而 runner 有四顆。八月那份報告寫「CPU 已飽和」，這次的量測不支持。第二，改內容的部署只有約 1% 的產物檔案真的變：一筆 57 篇的翻譯批次，32,186 個檔案裡 498 個不同，其中 144 個是同一份原始碼連建兩次也會不同的雜訊。

哲宇中途問每一頁還有沒有六月那種熱點。一次只建一頁量過、也做了 CPU 剖析：譯文每頁 4.2 毫秒，沒有任何單一函式超過 8%，那個等級的熱點已經沒有了。CI log 裡看似要 15 秒的頁是排隊造成的假象。

## 分片建置：從試到上線

做法是替每一份建一個全是符號連結的影子根目錄，只有 `src/pages` 各放一部分語言，四個 `astro build` 同時跑，再併回一份 dist，最後用 `astro.config.mjs` 裡同一份 sitemap 設定對全站產一次 sitemap（`scripts/core/build-sharded.mjs`）。沒有改任何頁面檔。

第一次試就抓到一個真的差異：`src/utils/staticRoutes.ts` 會看 `src/pages` 有哪些檔來決定連結要不要加語言前綴，分片後每個行程只看得到自己那一份，語言分片裡的導覽連結全掉了前綴、hreflang 不見。頁數、sitemap、URL 契約對賬都看不出來，是逐檔比對 HTML 才現形的。用環境變數指回真目錄修掉。

驗證做了四層：本機逐檔比對（20,554 頁內容相同，只差 CSS 檔名的分組）、sitemap 逐位元組相同、URL 契約 0 dead、以及新寫的 `scripts/tools/compare-build-styles.mjs` 在瀏覽器裡逐元素比全部樣式屬性（66 頁、兩種視窗、40 萬個元素，差異只落在儀表板與 semiont 頁進行中的動畫，對照組相同）。

在同款 runner 上的量測 run 46142747996：單次 241 秒、切四份 116 秒。比報告估的 150 秒少，因為四份同時跑時四顆核心全滿，每一份都變慢。

哲宇說「你來合並驗證」之後，21:44 合併 PR #2093（prebuild 的搜尋索引與最新文章清單併進平行區塊）與 #2094（部署的 Build 步驟改成分片）。合併後四次部署的中位：push 到上線 493 秒，Build 步驟 204 秒（原本 345）。正式站看過阿拉伯文文章、德文首頁、手機版中文文章，版面正常。打包那一步從 13 秒變成 25–32 秒，四次都是，原因還沒查。

## Beat 5 — 反芻

今晚最值得記的是 `staticRoutes.ts` 那一下。分片的前提是「每一頁的產出只跟它自己有關」，這個前提我沒有驗就開始切，而頁數、sitemap、URL 契約三把尺全部給了綠燈。抓到它的是最笨的那個動作：把兩份產物逐檔比對，然後打開一個不同的檔看差在哪。要是我只信那三把尺，語言頁的導覽連結會帶著錯的網址上線，而且每一道閘門都是綠的。這跟 REFLEXES #99「尺先驗再用」是同一件事的另一面：尺是真的、讀數也是真的，只是沒有一把在量我改壞的那個東西。

第二件是我自己寫的比對工具第一版把四十萬個元素全判成不同。原因是 CSS 變數的列舉順序跟著樣式表分組走，我把整串直接雜湊。要是那時候把它當成結論，會得出「分片把全站樣式改壞了」；拿一頁出來逐屬性看，是零差異。後來加的「同一份產物自己比自己」對照組，是這次驗證裡最有用的一步，它讓剩下那十幾個差異有了可以對照的基準。

估計值兩個都偏樂觀（分片估 150 秒實測 125，prebuild 重排估 25 秒實測 16）。兩次都是把「各段獨立」當成前提去相加，實際上四個行程會搶同一批核心。報告裡的 (b)、(c) 層還有好幾個同樣算法的估計，讀的時候該打個折。
