# CI/CD 極致加速評估（2026-11-28 開票夜）

哲宇問的是：taiwan.md 用最極致的建置與快取機制，部署可以快到什麼程度。這份報告只量、只算、只建議，沒有動 `.github/workflows/`，也沒有推 `main`。

每個數字後面都標了來源：

- **〔CI n=50〕**：最近 50 次成功部署的 GitHub Actions 紀錄
- **〔CI n=8〕**：抽 8 份建置 log 逐段解析
- **〔本機〕**：這台 M4 Max 上的實驗。同一時間有翻譯產線與開票迴圈在用 CPU，只拿比例，不拿絕對秒數
- **〔估〕**：推算，沒有實跑

## 一、結論

### 現在多慢

- 一次 push 到讀者看得到，中位 **10.4 分**、最慢 12.9 分〔CI n=50〕。
- 最近 150 次部署有 **62 次被下一筆 push 取消（41%）**。把取消算進去，同一批 push 的「推出去到真的上線」是中位 10.3 分、九成在 19.4 分內、最慢 **35.5 分**〔用 150 筆真實 push 時間重播〕。
- **部署完成不等於讀者看得到。** 站上每個回應都帶 `cache-control: max-age=600`，部署完成後主網址還可能吐舊版最多 10 分鐘（主 session 今晚 19:17 實測，見三之 I）。所以讀者端的最壞情況是上面的數字再加 10 分鐘。
- 今晚的痛點就是後面那個數字：多個 session 接力推，前一次部署還沒跑完就被取消，最慘的那筆等了三輪。

### 時間花在哪（一次成功部署的 622 秒）

| 段                                 | 秒  | 佔比 | 性質                            |
| ---------------------------------- | --- | ---- | ------------------------------- |
| Astro 產 20,554 頁                 | 239 | 38%  | 只用一顆核心，跟頁數成正比      |
| GitHub Pages 部署（deploy job）    | 126 | 20%  | 平台端，每次整包 6.1GB 重新同步 |
| prebuild（資料、儀表板、搜尋索引） | 97  | 16%  | 一條 54 秒的串行鏈卡住          |
| 打包＋上傳站體                     | 76  | 12%  | 每次整包上傳                    |
| Checkout＋環境                     | 50  | 8%   |                                 |
| 其他（驗證、排隊、快取）           | 34  | 6%   |                                 |

兩件以前沒有量過的事，決定了後面三層的排序：

1. **Astro 產頁幾乎只用一顆核心。** 本機全站建置 CPU 使用時間 141 秒、牆鐘 111 秒，約 1.3 顆核心；把 `concurrency` 從 8 改成 1，牆鐘只從 111 秒變成 125 秒，可見它是非同步排隊，不是平行〔本機〕。CI 的 runner 有 4 顆核心，照這個量測，產頁那 227 秒裡另外三顆大多閒著〔本機推論，CI 上沒有直接量過 CPU〕。08-04 那份報告寫「CPU 已飽和、concurrency 到頂」，本機的量測不支持那個判斷。
2. **改內容的部署只有約 1% 的產物檔案真的變了。** 拿兩筆真實部署前後各建一次比對：一筆翻譯批次（57 篇譯文）32,186 個檔案裡 498 個不同；一筆中文文章勘誤（一篇中文加一篇譯文）203 個不同。兩個數字都含 144 個「同一份原始碼連建兩次也會不同」的雜訊檔〔本機，各 n=1〕。動資料檔、動 `docs/semiont` 的部署沒有量。但現在每次都重建 20,554 頁、重傳 6.1GB。

### 三個層級各能到多快

| 層級                   | push 到上線（中位）                                                                | 最慢那筆                           | 代價                                         |
| ---------------------- | ---------------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------- |
| 現況                   | 10.4 分〔CI n=50〕                                                                 | 35.5 分                            |                                              |
| (a) 不改架構，一兩天   | 約 9.5 分〔估〕                                                                    | 約 20 分〔重播〕                   | 幾乎沒有                                     |
| (b) 中等改動，一到兩週 | 約 6.5 分；換部署平台約 4.5 分〔估〕                                               | 約 13 分；換平台後約 10 分〔重播〕 | 建置流程變複雜；換平台要花錢、要哲宇決定     |
| (c) 最極致             | 文章類改動 60–90 秒；自己的機器當 runner 25–40 秒；改成請求時才產頁 10–20 秒〔估〕 | 同左                               | 要自己維護「誰依賴誰」；最後一項放棄純靜態站 |

(a) 的誠實說法：中位數只能再擠出不到一分鐘。08-04 與 11-17 兩輪已經把不改架構的招式收得差不多了（含字型閘門的整趟從 14.4 分降到 11.1 分）。這一層真正值得做的是把「互相取消」解掉，讓最慢那筆從 35 分降到 20 分。

### 我推薦先做的三件

> **2026-11-28 20:20 哲宇決定：第 1 項不做，維持「新 push 取消進行中的部署」。** 下面第 1 項與三之 A 的分析留作紀錄，之後不必再提。互相取消的問題改靠縮短部署時間來緩解（部署越短，取消造成的等待越小，見三之 A 的重播表）。

1. **把部署改成排隊，不取消進行中的那一次。** `deploy.yml` 一行（`cancel-in-progress: false`）。GitHub 的行為是同一組最多一個在跑、一個在等，新的 push 進來會取代還在等的那個，所以不會越排越長。重播 150 筆真實 push：最慢從 35.5 分降到 20.6 分，白跑的 runner 時間從 122 分降到 0，中位數不變。這推翻哲宇六月選的「後推蓋前推」，所以要他點頭。
2. **在同一個 job 裡把 13 語切成 4 份同時產頁。** 不用矩陣、不用合併 2GB 的 artifact。預估產頁從 239 秒降到 90 秒上下，一次省約 150 秒，是不換平台的前提下最大的一筆〔估，依據是本機量到的單核心與線性〕。
3. **站體瘦身，並決定部署平台。** 站體 6.1GB，是 GitHub Pages 官方上限 1GB 的六倍，離「連試都不試」的 10GB 硬上限還有 1.6 倍的成長空間；11-10 已經連三次貼著 10 分鐘逾時。每頁 268KB 裡有 91KB 是每頁重複的內嵌腳本。瘦身自己可以做；換成只上傳差異檔的平台（Cloudflare Workers 靜態資產）要付費層，是哲宇的決定。佇列 #122 掛的是「部署包超過 1GB」這個問題本身；08-04 報告提的換平台方案（C1）我在佇列裡沒查到，建議主 session 補一筆。

高頻資料（開票數字這類）不該走部署這條路。今晚主 session 改成瀏覽器直接讀獨立資料分支，是對的架構，不是繞路，報告第五節把它列成常設做法。

### 2.4 取消與等待

- 150 次部署：87 成功、62 取消、1 進行中。逐日取消率：11-25 那天 41 次裡 20 次，今天 26 次裡 12 次。
- 被取消的 run 中位活了 112 秒才被取消，五天合計白跑約 122–144 分鐘。公開 repo 的 runner 免費，浪費的是等待，不是錢。
- push 的間隔中位 17 分鐘，但 41% 的間隔短於一次部署的時間，取消就集中在這些時段。
- `.husky/pre-push` 有「部署快跑完就等它」的機制，九月改成只在剩餘時間 ≤120 秒時才等。部署要 620 秒，前 500 秒進來的 push 照樣取消它，所以今晚擋不住，這是它現在的設計，不是壞掉。

| 實驗                                 | 頁數   | 牆鐘     | CPU（user） | 記憶體峰值 |
| ------------------------------------ | ------ | -------- | ----------- | ---------- |

### 2.8 平台的官方上限（今天查文件）

- GitHub Pages：發佈的站「不得大於 1GB」；部署超過 10 分鐘會逾時；artifact 超過 10GB「連試都不試」；每次部署吃完整的 artifact，沒有只傳差異的做法。來源：GitHub Pages limits、`upload-pages-artifact` README。
- GitHub Actions concurrency：同一組同時最多一個在跑；預設最多一個在等，新的進來會取代還在等的那個。`cancel-in-progress` 可以寫成運算式。
- 公開 repo 的標準 runner：x64 與 arm64 都是 4 核、16GB，免費不限量。「較大的 runner」文件只寫給 Team 與 Enterprise 方案，沒有寫對公開 repo 免費，報告當成付費項。
- Cloudflare Workers 靜態資產：免費層每版 20,000 檔、付費層 100,000 檔；單檔上限 25MiB；對靜態資產的請求免費不限量。Cloudflare Pages 的檔數與單檔上限相同，每月建置 500 次（免費）。付費層月費這次沒有在文件頁上查到，08-04 的報告寫 US$5，要用時再確認。

### G. 請求時才產頁（SSR 或邊緣端產生）

把 13 語的長尾文章頁改成讀者來的時候才由邊緣端產生、再快取。部署變成「把 Markdown 送上去」，10–20 秒〔估〕。

代價：

- 不再是純靜態站。現在任何人拿到 dist 就能在任何靜態主機重現整個站，這是 fork 友好的基礎，也是 GitHub Pages 能當免費備援的原因。
- 建置時內嵌的東西都要重做：404 頁的智慧建議、語意延伸閱讀、搜尋索引、sitemap、hreflang 的存在性檢查、URL 契約對賬。

只對長尾頁做（熱門頁仍預先產生）可以折衷，但兩套路徑並存的維護成本不低。我不建議走到這一步，除非 (b) 做完之後 4–5 分鐘仍然不夠。

### I. 部署完成後的快取（主 session 今晚回報，我補查了標頭）

主 session 的實測：19:15 部署完成，19:17 抓 `https://taiwan.md/elections/2026/` 拿到的還是 18:44 的舊版，標頭是 `cf-cache-status: HIT`、`age: 492`、`cache-control: max-age=600`；加查詢字串才拿到新版，19:19 快取過期後主網址才換新。

我 19:3x 抓了首頁、選舉專頁、一篇文章與一支儀表板 JSON〔線上實測，各一次〕：四個都是 `cache-control: max-age=600`；這四次的 `cf-cache-status` 是 `DYNAMIC`（Cloudflare 沒有快取這一次），跟主 session 看到的 `HIT` 不一樣。我沒有查出兩次為什麼不同（可能是 Cloudflare 後台有針對部分路徑的快取規則，我看不到後台），所以下面只講確定的部分。

確定的事：

- `max-age=600` 是 GitHub Pages 固定送的，在 GitHub Pages 上改不了。
- 它同時作用在三層：GitHub 自己的邊緣、Cloudflare（有快取到的時候）、讀者的瀏覽器。前兩層合起來，部署後最多 10 分鐘拿到舊版；看過舊版的讀者，瀏覽器還會再用自己那份最多 10 分鐘。
- 所以把部署從 10 分鐘壓到 4 分鐘之後，快取這 10 分鐘就變成最大的一段。這一項的優先度應該排在 B1 前後。

### J. 字型閘門（Font visibility gate）要不要留

哲宇今晚看 Actions 頁面時問它什麼時候加的、是不是不太需要。

它的來歷：2026-09-04 為 issue #1666 加的（commit `3f44f4388b`）。當時 `Layout.astro` 把整頁的顯示綁在字型載入事件上，沒有逾時出口，字型檔一慢，正式站就是永久空白，而所有 workflow 全綠。這道閘門在部署後打正式站三個網址，故意把字型檔卡住，量瀏覽器實際算出來的 `visibility`。

量到的事〔CI n=50〕：

- 中位 38 秒、最長 44 秒，排在 deploy 之後，**不擋上線**，不影響這份報告裡任何一個「push 到上線」的數字。它讓每次 run 在 Actions 頁面上多掛約 40 秒的進行中（主 session 說約兩分鐘，我量到的是 38 秒）。
- 最近 50 次全過；最近 150 次部署沒有任何一次失敗。
- 它驗的東西只跟自己的程式碼有關：字型是閘門自己卡住的，所以外部字型服務當天快或慢不會改變結果。九月以來 `Layout.astro` 改過 8 次。

建議：**保留這道檢查，但搬出部署 workflow**，改成獨立的 workflow，兩個觸發：

1. 動到 `src/layouts/`、全域樣式或字型載入相關檔的 push，在部署完成後跑一次。
2. 每天排程跑一次，當成保底（防有人從沒列到的檔案改壞它）。

## 九、只重建受影響的頁，做得到嗎（哲宇 23:05 問）

問題：只改一篇文章時，理論上其他文章都不必重建，只有跟這一篇相關的頁要更新。設計得夠好，應該做得到吧？

做得到，而且今晚的實測已經給了「受影響的頁」有多少：

| 這次部署改了什麼       | 產物裡真的變了的檔案                          | 佔全站 |
| ---------------------- | --------------------------------------------- | ------ |
| 一篇中文文章＋一篇譯文 | 約 60 個（203 個扣掉 144 個每次都變的雜訊檔） | 0.2%   |
| 57 篇譯文              | 約 350 個（其中 HTML 292 個）                 | 1.1%   |

所以「改一篇，重建幾十頁」是對的直覺。一篇文章會牽動的頁有這幾種：它自己、它的 13 個語言版本（hreflang 與語言切換互相指）、所屬的分類頁、首頁與最新文章頁、把它列在「延伸閱讀」的其他文章、changelog、sitemap，加上幾支 JSON（搜尋索引、最新清單）。

### 怎麼做

三個零件：

1. **留著上一次的 dist。** 每次部署後把產物存起來，下一次從它開始，只覆蓋變了的檔。
2. **算出這次該重建哪些頁。** 這是整件事的核心，也是唯一會出錯的地方。
3. **只建那些頁。** 今晚做的分片機制可以直接重用：分片是「這個行程只建這幾個語言」，增量是「這個行程只建這幾頁」，同一套影子目錄與併回邏輯。文章頁是動態路由，要在 `getStaticPaths` 加一個「只產這份清單」的過濾。

第 2 項有兩種做法：

| 做法       | 怎麼知道誰受影響                                                                                   | 風險                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 手寫規則   | 「改文章 X → 重建 X、X 的各語言版、X 的分類頁、首頁、列 X 當延伸閱讀的頁」                         | 規則會漏。今晚的 `staticRoutes.ts` 就是例子：沒人記得有一段程式在看整個頁面目錄 |
| 渲染時記帳 | 每頁渲染時記下「我讀了哪幾篇文章、哪幾支資料檔」，存成一份對照表；下次有檔案變了，反查哪些頁讀過它 | 要在讀資料的函式裡加記帳；沒走那些函式的讀取會漏記                              |

我建議第二種，再加兩道保險：

- **不認得的變動一律全站重建。** 變動只落在 `knowledge/` 的文章檔才走增量；動到模板、元件、設定、資料檔、腳本，就照現在的全站建置。今晚的統計裡，只動文章與譯文的部署佔 43%。
- **定期用全站建置對答案。** 每天一次全站重建，跟增量累積出來的 dist 逐檔比對，不同就報警並以全站那份為準。這就是今晚抓到 `staticRoutes.ts` 的那個動作，變成常設的。

### 能快多少，卡在哪

增量建置只省「astro 產頁」那一段，現在是 204 秒裡的約 110 秒。其他幾段照舊：

| 段                | 現在   | 只做增量建置            | 再加只傳差異檔的平台 |
| ----------------- | ------ | ----------------------- | -------------------- |
| checkout 與環境   | 50     | 50                      | 50                   |
| prebuild          | 80     | 80                      | 80                   |
| 取回上一次的 dist | 0      | 約 50（2GB 快取）〔估〕 | 0（不用取回整份）    |
| astro 產頁        | 約 115 | 約 20〔估〕             | 約 20                |
| 打包＋上傳        | 94     | 94                      | 約 10〔估〕          |
| Pages 部署        | 132    | 132                     | 約 20〔估〕          |
| 合計              | 約 490 | 約 430                  | 約 180（3 分）       |

結論是順序很重要：**在 GitHub Pages 上單做增量建置幾乎沒有賺頭**，因為省下的建置時間被「取回 6GB 的舊產物」吃掉大半，而每次仍要整包上傳、整包部署。GitHub Pages 只收完整的一包，沒有「只換這幾個檔」的做法。要讓增量建置有意義，得先換成只傳差異檔的部署方式（報告 §三之 C3），那時候連舊 dist 都不必取回，只要一份「每個檔的雜湊」清單。

再往下是 prebuild 那 80 秒：它現在每次掃全站（文章健檢、儀表板、搜尋索引）。要壓到一分鐘以內，prebuild 也得做成增量的，那是另一輪工程。

### 所以建議的路

1. 先決定部署平台（§三之 C3）。這是前提。
2. 做「渲染時記帳」拿到依賴對照表，先不拿來跳過建置，只拿來跟實際變動的檔案對答案，跑一兩週看它準不準。
3. 準了再開啟增量，全站重建留作每天的對答案與不認得變動時的退路。

站體瘦身（§三之 C1、C2）跟這條路互不衝突，而且會讓雜訊檔與 changelog 這種每次都變的大檔變少，差異上傳才真的小。

## 十、把 mouhouse 當建置機，有沒有幫助（哲宇 23:10 問，量過、還沒設定）

先講清楚稍早那個「25–40 秒」：那是 (c) 層「增量建置＋只傳差異檔＋熱的自架機器」三件事疊起來的估計，不是光換機器就有。這一節只量「換機器」這一件。

做法：沒有註冊 runner。在 mouhouse（Mac mini M2 Pro，12 核 32GB）上另開一份獨立的 clone，照部署 build job 的步驟跑一遍〔mouhouse 實測，n=1，當時機器負載約 1〕：

| 段                      | GitHub runner（合併後中位，n=4） | mouhouse                                            |
| ----------------------- | -------------------------------- | --------------------------------------------------- |
| 取碼（checkout）        | 35 秒                            | 1.2 秒（工作目錄是熱的）                            |
| 環境（node、快取還原）  | 約 15 秒                         | 0                                                   |
| prebuild                | 約 80 秒                         | 53 秒                                               |
| 分片建置                | 約 115 秒                        | 46 秒（切 8 份是 42 秒，差不多）                    |
| URL 契約對賬            | 約 9 秒                          | 6 秒                                                |
| 打包                    | 32 秒                            | 13 秒                                               |
| **以上小計**            | **約 286 秒**                    | **約 120 秒**                                       |
| 上傳產物（約 2GB）      | 62 秒                            | 沒量。上行頻寬 265 Mbps，換算約 65 秒再加壓縮〔估〕 |
| Pages 部署（GitHub 端） | 132 秒                           | 不變                                                |
| push 到上線             | 493 秒                           | 約 330 秒（5.5 分）〔估〕                           |

所以有幫助，一次大約再省 2.5 分鐘。剩下的 5.5 分鐘裡有 3 分多鐘是「上傳整包＋Pages 部署」，換機器動不到，那一段只有換部署方式才會變。

沒有直接設定的原因，是這幾件事要哲宇先知道：

1. **公開 repo 掛自架 runner 有安全風險。** 外部的 PR 可以改 workflow 檔，把工作指到自架機器上跑，等於讓陌生人的程式在 mouhouse 上執行。那台機器上有 GitHub App 私鑰、Supabase 憑證、Claude 的登入。GitHub 官方文件不建議公開 repo 用自架 runner。要做的話至少要：repo 設定改成「所有外部貢獻者的 PR 都要核准才跑 workflow」，runner 用獨立的使用者帳號跑、碰不到那些憑證。
2. **會跟 routine 與翻譯產線搶機器。** 量測時負載從 1 衝到 21。一天約 30 次部署，每次兩分鐘滿載，翻譯產線與排程班會變慢。
3. **機器不在線時部署會卡住。** GitHub 沒有「自架機器離線就自動改用雲端機器」的內建機制，工作會一直排隊。要自己加一個前置步驟先查 runner 在不在線，再決定跑哪邊。mouhouse 八月黑過四天，12-02 登入又要過期。
4. **node 版本不同。** mouhouse 是 node 24，CI 釘 22.23.4。要在 runner 上裝同一版，產物才可比。
5. 註冊 runner 等於替 repo 新增一個機器身份，照自主權邊界是哲宇的決定。

量測留下的東西：mouhouse 上 `~/ci-bench-twmd`（1.7GB 的獨立 clone，共用 routine repo 的物件庫，沒有動 routine 的工作目錄）與 `~/ci-bench*.log`。要設 runner 的話可以直接拿來當工作目錄，不設就刪掉。
